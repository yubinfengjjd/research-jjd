# 主线版本规则：早期版本与开发史不进成品

适用于整套流程：规划（medfig-plan）、渲染（medfig-render）、批量出图与审查（medfig-orchestrate）、写作大纲（medfig-outline）。

## 1. 规则

1. **只呈现主线。** 规格 §0 的"版本清单"指定唯一的主线模型 / 分析版本。早期版本、失败的旧方案、修复前的模型、内部开发阶段的产物一律**丢弃**：不进图、表、图注、写作大纲，不当对照、补充实验或"修复前后"比较，也不在正文里提及。
2. **按科学问题组织。** 内部计划编号映射到实际科学问题；真实预注册、预设终点及验证性设计是研究设计证据，应按协议如实保留，不与内部修复日志混同。不得把事后分析改写成预设分析，也不得仅因“预注册”一词删除设计信息。
3. **开发记录与研究设计分开。** 内部wave、repair/修复、版本裁决等日志不进入读者正文；Methods关联代码可保留真实分析代码、配置和回执路径。探索性、事后分析和预设推断状态按实际设计、执行和结论分别说明，不把全部研究或所有次要终点自动标为探索性。范围声明可支配明确同分析组，换范围时重申；独立图注/表注仍需自身必要限定，不规定只在Methods说一次。
4. **规划时一次问清。** 版本清单是 medfig-plan 第 2 步的必问项；用户已经回答过的不再重复问。用户没答之前，不渲染任何涉及版本比较的 panel。

## 2. 落实方式

| 环节 | 做法 |
|---|---|
| 规格（medfig-plan） | §0 写版本清单：主线、丢弃项、"内部计划名 → 科学问题"对照；§2 的代号对照表包含这些名称 |
| 项目配置 | 把丢弃版本的名称和开发阶段代号写进 `figkit.toml` 的 `[qa] forbidden_patterns`（例如 `'Wave-?\d'`、`'(?i)earlier <模型名>'`）；figkit 默认已拦截开发史通用词（`qa.DEV_HISTORY`） |
| 渲染（medfig-render） | 导出时 `qa.figure_text_audit` 报 `development history` 即失败；修法是删掉该元素或改成科学问题措辞，不是放行 |
| 表格 | 读者版 md / tex 用同一套 `forbidden_in_text` + 开发史词检查；内部审计表（口径裁决、溯源索引）不对读者，可保留 |
| 审查（medfig-orchestrate） | 终审清单第 4 节逐项核对：没有丢弃版本、没有按内部计划组织的行、图注没有开发史 |
| 写作大纲（medfig-outline） | 小节按科学问题划分，标题写本节发现；大纲检查脚本拦截同一组词 |

## 3. 常见借口

| 借口 | 实际 |
|---|---|
| "和早期版本比提升很大，放补充实验更有说服力" | 早期版本和主线差的是一批修复，不是一个设计选择，讲不出因果；还会引出"第一版为什么失败"。设计选择用消融实验呈现 |
| “预注册假设要照实报告” | 保留真实预注册设计、结果及阴性证据；内部编号可映射为科学问题，不删研究设计事实 |
| “图注里需说明事后探索性分析” | 按实际分析时间及读者理解主张所需范围保留；不得用开发流程禁词覆盖研究设计 |
